## B. 我的实现离"生产可用"还差什么

> 这一节是今天最值钱的部分。**主动说缺点比吹功能更加分**。
> 你的原始作答「没有日志」「异步状况下没有保护」——方向都对，下面补上"后果 + 怎么补"。

| # | 缺口 | 后果 | 生产上怎么补 |
|---|---|---|---|
| 1 | 没有并发保护（`asyncio.Lock` 被我注释掉了） | 两个协程同时读到 `_failure_count=4` 再加 1，最终只变 5 但两次失败被记成一次 → 该熔断时没熔断；半开配额也可能被超放 | 用 `async with self._lock` 包住状态的读改写（原版就是这么做的） |
| 2 | 状态只存在进程内存里 | 网关多副本时，三个进程三份独立熔断状态 → 上游对 A 挂了，B、C 还在往它发流量 | Redis 共享计数/状态；或架构上保证**单入口**（你的网关本身就是统一入口，弱化了问题但没消除） |
| 3 | 用 `time.time()` 算冷却 | 系统对时 / NTP 回拨会让时间差变负 → 永远不晋升 → 通道**永久熔断** | 换 `time.monotonic()`（只增不减，不受对时影响） |
| 4 | 熔断状态不持久化 | 网关重启瞬间状态清零 → 全部流量立刻砸向可能仍在故障的上游 | 启动时从共享存储恢复；或重启后先按"保守半开"起步 |
| 5 | 不区分错误类型 | 429/401 也算失败 → 上游只是限流，你却把整个通道熔断，反而更糟 | 只把 5xx / 连接失败 / 超时计入熔断；429 走退避，401 走换 key |
| 6 | 没有指标与日志上报 | 只知道"熔断过"，不知道熔断几次、开了多久、半开成功率多少 → 没法调阈值 | 状态转换打日志 + 暴露指标（熔断次数 / open 时长 / 半开成功失败比），即 Roadmap 里的 Prometheus |

## C. 三个必被追问的问题（先写自己的答案，再对照）

**Q1. 如果 `failure_threshold` 设成 1 会怎样？**

你的答案：失败一次就会熔断 ✅
补齐：一次网络抖动就触发熔断，恢复还得等冷却 + 走半开 → 上游稍微打了个嗝，你就反复熔断/恢复（这叫 **flapping 抖动**）。
所以 threshold=1 只适合"**必须快速止损**"的场景（计费、转账、危险操作），不适合抖动的公网 API。

**Q2. 如果 60 秒冷却期内所有请求都失败，断路器会不会一直 `OPEN`？谁负责把它变回 `HALF_OPEN`？**

你的答案：会，等待有效冷却后（方向对，但"谁"没答）
补齐：**不会永久卡住，但也没有谁"主动"去改它**。冷却到期后是**下一次有人读 `state` 属性时**才晋升半开；如果这次探测又失败 → 回 `OPEN` 且冷却重新计时 → 于是形成 `OPEN → HALF_OPEN →（失败）→ OPEN` 的循环。
所以准确的表述是：**它在"反复试探"，不是"一直不动"**；每次失败都要再等一个完整冷却期。

**Q3. 多进程 / 多实例部署时，这套断路器还有效吗？**

你的答案：有效，这是同一个网关，可以在上游就熔断（对了一半，缺前提）
补齐：**单进程有效**——因为 `breaker_manager` 是模块级全局字典，一个进程一份。
**多副本就失效**：每个进程各熔各的，上游对 A 副本挂了，B、C 还在往它发流量。
**但你的回答里有个真东西**：你的网关是**统一入口**架构，只要所有业务流量都经过同一个网关进程，"多进程"就不存在，问题被架构弱化了。所以标准说法是：
> "单入口架构下是有效的；一旦网关做多副本（HA/负载均衡），就必须把计数放到 Redis 共享——统一入口只是让问题变小，不是消失。"

（这才是加分的回答：既知道风险，也知道自己的架构为什么能扛一部分。）

> 提示（Q3）：`breaker_manager` 是模块级全局字典，每个进程各有一份。三个实例 = 三份互不知情的状态 → 上游对 A 实例挂了，B、C 还在往它发流量。这叫"**熔断器没有共享状态**"，生产上要么用 Redis 共享计数，要么由网关侧统一入口（你的架构恰好是后者，这是一个可以讲的加分点）。

## D. 30 秒讲稿（照着念顺为止）

> "断路器是我自己重写的，三态机：`CLOSED` 全放行、`OPEN` 全拒绝、`HALF_OPEN` 只放一个探测。
> 设计上有三个点我想强调：
> 第一，**冷却到期的晋升是惰性的**——写在 `state` 属性里，读取时顺手检查，不用后台定时器，少一类线程 bug；
> 第二，**冷却到期不等于恢复**，只能进半开，必须靠一次成功探测才能回 `CLOSED`，否则会二次雪崩；
> 第三，**半开探测失败要重新计时**，实现上就是把失败时间戳写在 `record_failure` 的第一行，一行搞定。
> 我用 mock 上游 + 配置注入做了故障注入验证：前 5 次自动切备用、第 5 次熔断、第 6 次直接跳过主通道，6 次请求全部 200，用户无感。
> 我也知道它的短板：状态在进程内存里、没有跨实例共享、没有区分 429 这种"不该熔断"的错误——生产上我会把计数放 Redis，并把错误分类做进去。"
