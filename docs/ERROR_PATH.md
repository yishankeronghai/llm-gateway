# 错误链路与状态码语义（面试讲解材料）

> 一句话：**错误处理的分层，就是"谁负责发现、谁负责分类、谁负责翻译成协议"。**
> 只要有一层越界（比如 provider 偷偷把错误塞回返回值），整条链路就会退化成"HTTP 200 装错误文本"。

---

## 一、四站职责（各管一层，不越界）

```
                    ┌─────────────────────────────────────────────┐
   请求进来          │  ① provider.py   发现错误 + 分类(kind)      │
                    │       ↓ raise UpstreamError(kind, msg, ...) │
                    │  ② router.py     接住 + 记录 + 换下一个通道 │
                    │       ↓ RouteResult.failure_kind            │
                    │  ③ completions.py  kind → HTTP 状态码 + 错误体│
                    │       ↓ status_code                         │
                    │  ④ audit         记录真实状态码             │
                    └─────────────────────────────────────────────┘
```

| 站 | 只负责 | 绝对不负责 |
|---|---|---|
| ① provider | 发请求、判成败、**分类**失败原因 | 决定 HTTP 状态码 |
| ② router | 故障转移、断路器记账、**传递**原因 | 翻译协议、决定状态码 |
| ③ completions | **翻译**成 HTTP 语义 + 统一错误体 | 重试、切换通道 |
| ④ audit | 记录**真实**结果（供统计/告警） | 影响响应 |

---

## 二、核心设计原则：返回值表达结果，异常表达失败

改前的 bug：

```python
# provider.py（旧）
return error_response, latency_ms, False     # 把"事故"包装成一个"正常结果"
# completions.py（旧）
if route_result.response:                    # 只要对象有值就当成功
    return 200                               # → 上游挂了却返回 200
```

改后：

```python
raise UpstreamError(kind, message, status_code, latency_ms)   # 事故不能被当成结果
```

> **为什么异常是对的**：返回值可以被忽略、可以被当成 None 糊过去；异常强制调用方处理，
> 否则请求直接 500。**它不可能被"顺手当成正常结果"用掉。**

## 三、状态码映射表（kind → HTTP）

| kind（失败原因） | HTTP | 谁的责任 | 调用方应该做什么 |
|---|---|---|---|
| `timeout` | **504** | 上游（太慢） | 可重试；或降级/换小模型 |
| `connect` | **502** | 上游（连不上） | 可重试（配合退避） |
| `upstream_5xx` | **502** | 上游（自己崩了） | 可重试 |
| `upstream_429` | **502**（不透传 429） | 上游限流 | 退避后重试，别对自己限流 |
| `upstream_auth` | **502** | 我方配置错（key 无效） | 不要重试，立即告警给运维 |
| `upstream_4xx` | **502** | 请求本身有问题 | 不要重试，修请求 |
| `unknown` | **502** | 未知 | 上报 + 重试一次 |
| `all_unavailable` | **503** | **我方**（全熔断/未配置） | 稍后重试；这是"网关现在没能力服务" |

### 502 vs 503 的唯一判别法

> **问自己一句："这次请求，我到底有没有往上打？"**
> - **打了**，对面上游失败 → **502**（上游的锅）
> - **没打**（被断路器拦下 / 根本没配通道）→ **503**（我的锅）

记忆口诀：**502 = 上游的锅；503 = 我的锅。**
（和流式、首 token 没有任何关系——那是另一回事。）

### 为什么 `STATUS_BY_KIND.get(kind, 502)` 的默认值是 502

出现未知 kind 时，宁可报"上游坏了"，也不报 200。**默认值的选择本身就是一条安全策略**——这是 fail-closed 思路在状态码上的体现。

## 四、错误体字段：每个都有主

```json
{
  "error": {
    "code": "upstream_unreachable",
    "kind": "connect",
    "message": "[openai-primary] 连接失败: All connection attempts failed",
    "trace_id": "9d9e0d69",
    "attempted_channels": ["deepseek-primary", "openai-primary"],
    "latency_ms": 4064.27
  }
}
```

| 字段 | 给谁用 | 为什么必须有 |
|---|---|---|
| `code` | **机器**（调用方分支逻辑） | 稳定、可枚举；用 message 做判断一改文案就崩 |
| `kind` | 运维/排查（更细的分类） | `upstream_429` 和 `upstream_5xx` 都是 502，但处置方式不同 |
| `message` | **人**（用户/客服/日志） | 能直接看懂发生了什么 |
| `trace_id` | 定位 | 用户报障只说"我刚刚失败了"，你用这个 id `grep` 一次就能拿到**这一次请求的全链路**：认证→限流→路由→每个通道的尝试→审计落库 |
| `attempted_channels` | 定位**空间** | 回答"重试过谁、顺序如何、是不是备用也挂了" |
| `latency_ms` | 判断性质 | 4000ms 说明已经等了两轮连接超时，不是瞬间失败 |

> `trace_id` 管**时间线**，`attempted_channels` 管**空间（试过谁）**，两者互补。

## 五、为什么上游 429 不原样透传给调用方

**因为 429 的语义是"你（调用方）被限流了"，而实际是"上游在限我们"。**

透传会引发三个错误后果：

1. **甩锅**：调用方会以为自己在网关的配额超了，去调整**自己的**并发/退避策略——方向完全错。
2. **语义冲突**：网关**自己的**限流也会返回 429（第 2 站）。两个 429 混在一起，调用方无法区分"被网关限"还是"被上游限"。
3. **错过正确处置**：上游限流该由**网关**处理（退避 retry-after、切到其它通道），不该让调用方知道。

正确做法：**502 + `code: "upstream_rate_limited"`**，让调用方知道"这是网关的上游问题"，网关内部去退避/切换。

> 进阶（Roadmap）：上游 429 应当视为"该通道**暂时不可用**"的信号 → 做退避或临时降权，
> 但**不应计入断路器失败**（429 是限流不是故障，熔断整条通道反而更糟）。这就是 W2 里那条"错误分类"缺口的真实价值。

## 六、三个常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| `except` 顺序错（父类写在子类前） | 超时被当成连接错误 → 504 变 502 | **具体的在前，父类兜底在后** |
| catch-all 吞掉自己的 bug | router 里 `except Exception` → 你的 `KeyError` 被伪装成"上游 502" | 只捕获**认识**的异常，让未知异常崩出来 |
| `raise` 丢失原始堆栈 | 排查时看不到最初那个异常 | `raise UpstreamError(...) from e` |

## 七、30 秒面试话术

> "我修过一个很典型的错误语义 bug：上游失败时，网关把错误包装成正常响应体返回，最终 HTTP 200 装着错误文本。后果是调用方没法用状态码重试，监控里全是绿的。
> 我的改法是把'失败'从返回值改成异常——**返回值表达结果、异常表达失败**；然后按失败类型映射状态码：超时 504、上游失败 502、所有通道熔断 503，并返回结构化错误体，带 `code`、`trace_id`、`attempted_channels`。
> 有个细节我特意区分了：**502 是上游的锅（我打了，它坏了），503 是我的锅（我根本没法打）**；上游 429 我不透传，因为那会让调用方误以为是自己被限流，方向就错了。"
